## 1. SQL-ін'єкції

- **Payload:** `http://127.0.0.1:8000/index.php?genre=' OR '1'='1`
- **До:** таблиця порожня, тобто значення оброблено як звичайний текст. Вразливості немає: усі запити практикуму 4 підготовлені.
- **Додатково (за кодом):** запити практикумів 5–7 також підготовлені (`prepare()` + `execute()`/`bindValue()`), конкатенації `$_GET`/`$_POST` у SQL немає.
- **Посилення:** у `db.php` вимкнено емуляцію підготовлених запитів, тож значення передаються СУБД окремо від тексту запиту.

```php
$stmt = $pdo->prepare('SELECT * FROM movies WHERE genre = :genre ORDER BY id DESC');
$stmt->execute([':genre' => $genre]);

// db.php
PDO::ATTR_EMULATE_PREPARES => false,
```

- **Після:** той самий payload дає порожню таблицю.

## 2. XSS

- **Payload:** назва фільму `<img src=x onerror=alert(1)>` (режисер «в», рік 2000, жанр «і», рейтинг 3).
- **До:** назва показується як текст, вікно alert не з'являється: вивід уже був екранований `htmlspecialchars()`.
- **Посилення:** усе виведення йде через одну функцію `e()` з явними прапорцями (екрануються й лапки, тож безпечно й усередині HTML-атрибутів).

```php
function e(mixed $value): string
{
    return htmlspecialchars((string) $value, ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8');
}
// <td><?= e($movie['title']) ?></td>
```

- **Після:** той самий рядок у таблиці виводиться текстом, alert не з'являється.

## 3. CSRF

- **Payload:** локальна HTML-сторінка `csrf-test.html` з прихованою формою, яка автоматично надсилає POST на `http://127.0.0.1:8000/add.php` (поля `title`, `director`, `year`, `genre`, `rating`, без токена).
- **До:** запис «CSRF-фільм» додано без жодної перевірки.
- **Виправлення:** токен у сесії для всіх форм, що змінюють дані (додавання, редагування, видалення, оцінка), перевірка через `hash_equals()`, відповідь 403 при відсутності або підробці. Додатково cookie сесії має `SameSite=Lax` і `HttpOnly`.

```php
function csrf_token(): string
{
    if (empty($_SESSION['csrf_token']) || !is_string($_SESSION['csrf_token'])) {
        $_SESSION['csrf_token'] = bin2hex(random_bytes(32));
    }
    return $_SESSION['csrf_token'];
}

function csrf_verify(): void
{
    $expected = $_SESSION['csrf_token'] ?? '';
    $sent = $_POST['csrf_token'] ?? '';
    if (!is_string($expected) || $expected === '' || !is_string($sent) || !hash_equals($expected, $sent)) {
        abort(403, 'Недійсний CSRF-токен. Оновіть сторінку й спробуйте ще раз.');
    }
}
// у формі: <?= csrf_field() ?>   в обробнику: csrf_verify();
```

- **Після:** той самий `csrf-test.html` приводить на сторінку «Недійсний CSRF-токен. Оновіть сторінку й спробуйте ще раз.»; у списку лишається один «CSRF-фільм» — новий не додано. Форма «Оцінити» (доменна дія з практикуму 6) захищена так само.

## 4. Видалення через GET

- **До (за кодом):** `delete.php` читав `$_GET['id']` і виконував `DELETE`, а в списку було звичайне посилання `delete.php?id=N`; досить відкрити адресу (навіть випадково чи через бота), щоб запис зник.
- **Виправлення:** видалення лише через POST з CSRF-токеном і підтвердженням у браузері.

```php
// delete.php
require_post();   // не POST → 405, заголовок Allow: POST
csrf_verify();

// index.php
<form method="post" action="delete.php" onsubmit="return confirm('Видалити цей фільм?')">
    <input type="hidden" name="id" value="<?= (int) $movie['id'] ?>">
    <?= csrf_field() ?>
    <button type="submit">Видалити</button>
</form>
```

- **Після:** `delete.php?id=1` в адресному рядку показує «Ця дія доступна лише через POST.» і нічого не видаляє; кнопка «Видалити» запитує підтвердження й працює через POST.
- `confirm()` сам по собі не є захистом: справжній захист тут — POST і CSRF-токен.

## 5. Валідація форм на сервері

- **Payload:** POST напряму (з дійсним токеном, у обхід HTML-атрибутів `required`/`min`/`max`):
  - `year=99999999999`, `rating=-5`;
  - `title[]=x` (масив замість рядка).
- **До (за кодом):** рік перевірявся лише `is_numeric()`, тож значення поза діапазоном колонки викликало б помилку БД; масив у `trim()` — необроблену помилку типу.
- **Виправлення:** єдина функція перевірки на сервері: рядки — це текст не довший за колонку, рік — ціле від 1888 до поточного, оцінка — число від 0 до 10.

```php
foreach (['title' => 255, 'director' => 255, 'genre' => 100] as $field => $maxLength) {
    $value = $input[$field] ?? null;
    if (!is_string($value) || trim($value) === '') {
        $errors[$field] = 'Обов\'язкове непорожнє текстове поле';
    } elseif (mb_strlen(trim($value)) > $maxLength) {
        $errors[$field] = "Максимум {$maxLength} символів";
    }
    // ...
}
```

- **Після:** обидва запити повернули відповідь 200 з повідомленнями про помилки (`Ціле число від 1888 до 2026`, `Число від 0 до 10`; для масиву — `Обов'язкове непорожнє текстове поле`). `INSERT` виконується лише тоді, коли масив помилок порожній, тож «сміття» в базу не потрапляє.

## 6. Обробка помилок

- **До (за кодом):** `db.php` виводив `$e->getMessage()`, інші сторінки не перехоплювали винятки, тож користувач міг побачити текст помилки PDO і шляхи до файлів.
- **Виправлення:** помилки PHP не показуються користувачу, а єдиний обробник виключень пише деталі в лог і віддає загальний текст.

```php
ini_set('display_errors', '0');

set_exception_handler(function (Throwable $e): void {
    error_log(get_class($e) . ': ' . $e->getMessage() . ' у ' . $e->getFile() . ':' . $e->getLine());
    http_response_code(500);
    echo 'Сталася внутрішня помилка. Спробуйте пізніше.';
});
```

- **Після:** при тимчасово перейменованому `config.local.php` сторінка показує лише «Сталася внутрішня помилка. Спробуйте пізніше.», без шляхів і технічних подробиць; причина видна лише в журналі сервера.

## Додатково

- **Пароль до БД** більше не лежить у коді: `db.php` читає `config.local.php`, якого немає в репозиторії (є лише зразок `config.example.php` і запис у `.gitignore`).
- **`schema.sql`** відтворює таблицю `movies` з нуля та містить індекси `idx_movies_genre` (для `findByGenre()` і `listGenres()`) і `idx_movies_rating` (для `topRated()`).
- Сторінки практикуму 4 перероблено в `practicum08` разом з доменною дією «Оцінити» з практикуму 6.

## Обмеження

- Застосунок не має автентифікації, тож токен прив'язаний до сесії, а не до користувача.
- API з практикумів 5–7 не використовує сесій і в цій роботі не змінювався: запити там підготовлені, відповіді — JSON без технічних деталей (практикум 7). Захист від CSRF для API вимагав би автентифікації й тут не реалізований.
- Перевірки, позначені «за кодом», виконано переглядом коду практикуму 4 без запуску.
- Тестування виконано вручну, в одному браузері.
